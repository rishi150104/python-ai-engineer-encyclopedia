## Definition and purpose

Every Python object has an **identity**, a **type** and a **value**. The identity never changes once the object exists, and `id()` returns an integer representing it `[C1]`. The `is` operator compares identities `[C2]`. The `==` operator compares **values**, as defined by the type's comparison implementation `[C7]`.

An object is **mutable** if its value can change in place, and **immutable** if it cannot. Mutability is a property of the type: numbers, strings and tuples are immutable; lists and dictionaries are mutable `[C5]`.

Why this matters: almost every Python bug of the form "I changed one thing and another thing changed too" is an aliasing bug. This entry gives the model needed to predict the behavior instead of memorizing cases.

## Mental model

1. **Objects live somewhere; names are labels bound to them.** Assignment does not copy an object. It binds a target to an object `[C12]`, and assignment statements (re)bind names and can also modify attributes or items of mutable objects `[C13]`.
2. **Three different operations** are easy to confuse:
   - *rebinding* (`x = ...`): the name points at a different object; no other name is affected.
   - *mutation* (`x.append(...)`, `x[i] = ...`): the same object changes; every name bound to it sees the change.
   - *copying*: creates a new object (see below).
3. **Identity is about the object; equality is about the value.** Two distinct objects can be equal; one object is (normally) equal to itself.

```text
a = [1, 2]         a ─┐
c = a                 ├─▶ [1, 2]  (one list, two names)
b = [1, 2]         b ───▶ [1, 2]  (a second, equal, distinct list)
```

## Identity vs equality

- `x is y` is true if and only if `x` and `y` are the same object `[C2]`. `id()` is unique and constant for an object during its lifetime, but objects with non-overlapping lifetimes may have the same `id()` `[C3]`. `[J]` Do not store an `id()` as a long-term key.
- In CPython `id(x)` is the object's memory address, but that is an implementation detail `[C4]`, so `[J]` do not rely on it.
- Default `==` (for objects of types that do not override it) is based on identity; many built-in types override it to compare values `[C7]`.
- The default equality behavior is motivated by `x is y` implying `x == y`; `float('nan')` is the documented exception: `nan == nan` is false and `nan != nan` is true `[C8]`.
- Built-in containers *typically* assume identical objects equal themselves and bypass the equality test for them `[C9]`. In E1 this makes `[nan] == [nan]` and `nan in [nan]` true (observed). For list, tuple, set, frozenset, dict and deque, `x in y` is documented as equivalent to `any(x is e or x == e for e in y)` `[C9]`. "Typically" means a custom container is not guaranteed to behave this way.
- Compare singletons such as `None` with `is` / `is not`, never `==` (PEP 8 advice recorded in the language reference) `[C10]`.
- Whether `a = 1; b = 1` makes `a is b` true is implementation-dependent for immutable types. After `c = []; d = []` the lists are guaranteed distinct; `c = d = []` binds one list to both names `[C11]`. `[J]` Because of the "may or may not", do not use `is` to compare numbers or strings.

**E1** (`e1_identity_vs_equality.py`), output as recorded:

```text

False True True True
True True
```

Line 1: equal-but-distinct lists, and an alias. Line 2: the NaN cases. Line 3: `x is None` and `x == None` agree here, but only `is` follows the documented style advice `[C10]` (and `==` can be overridden by a custom class `[C7]`).

## Mutability

- Mutable and immutable are per type `[C5]`.
- A **tuple is immutable but not "deeply constant"**: if it holds a mutable object and that object changes, the tuple's value changes. The container's mutability concerns only the identities of its immediate items `[C6]`.
- `+=` is not "always rebind" or "always mutate": augmented assignment performs the operation in place when possible `[C14]`. For a list, `s += t` extends `s` `[C16]`; for a `str` it rebinds to a new string (inferred from immutability, confirmed by E2) `[C31]`. `lst = lst + [3]` builds a new list and rebinds (E2).
- A name rebound inside a function or loop never affects other names; a mutation always does. Ask "did the object change, or did the name move?"

**E2** (`e2_rebinding_vs_mutation.py`):

```text
abc ab False
[1, 2] [1, 2] True
[1, 2, 3] [1, 2] False
```

**E3** (`e3_tuple_with_list.py`), the classic edge case:

```text
([1, 2],)
TypeError
([1, 2, 3],)
unhashable key
```

`t[0] += [3]` first extends the list in place, then tries to store the result back into the tuple, so the list is already changed when the store happens `[C15]` (inferred from the documented evaluation order, confirmed by E3). That the failing store raises `TypeError` is **observed** (E3 on 3.11 and 3.13); the quoted documentation does not name the exception. A tuple containing a list also cannot be a dict key (see Hashing).

## Copying

| Operation | Result | Nested objects |
|---|---|---|
| `b = a` | no copy, second name | same everything |
| `a.copy()`, `a[:]`, `dict.copy()`, `copy.copy(a)` | new outer container | **shared** (shallow) `[C19]` `[C17]` |
| `copy.deepcopy(a)` | new outer container and recursive copies | independent `[C17]` |

- A shallow copy builds a new compound object and inserts references to the original's items; a deep copy inserts recursive copies. The distinction only matters for compound objects `[C17]`.
- `deepcopy` keeps a memo so recursive structures terminate, and can "copy too much" (data meant to be shared between copies). A class can customize both via `__copy__` and `__deepcopy__` `[C18]`.
- **Repetition does not copy:** in `[[]] * 3` the items are referenced multiple times, not copied `[C20]`. A comprehension (`[[] for _ in range(3)]`) creates three lists (E4).
- `[J]` `deepcopy` cost grows with the size of the object graph it walks (not stated in the sources). Decide deliberately where to copy (see production section).

**E4** (`e4_copying.py`):

```text
[[1, 2, 99], [3]] [[1, 2], [3]]
False True False
True True
[['x'], ['x'], ['x']] True
[['x'], [], []]
True True
```

Reading it: the shallow copy sees the nested change (`shallow[0] is nested[0]`); the deep copy does not. Slicing and `.copy()` are shallow. `[[]] * 3` aliases one list. A self-referencing list deep-copies without infinite recursion and the copy refers to itself, not the original.

## Function arguments

Arguments are passed **by assignment**: each parameter name is bound to the caller's object. There is no alias between the caller's name and the callee's name, so there is no call-by-reference per se `[C21]`.

- Rebinding the parameter (`items = [0]`) does not affect the caller `[C21]`.
- Mutating the object (`items.append(0)`) does affect the caller, because both names refer to the same object `[C32]` (E5).
- `[J]` To hand new values back, return them (a tuple if several) instead of trying to emulate output parameters; the FAQ suggests returning a tuple as one option.

### Mutable default arguments

Default parameter values are evaluated **once**, when the `def` runs, and the same object is used on every call `[C22]`. If the function mutates a mutable default, the default itself is modified `[C22]`. The FAQ recommends not using mutable objects as defaults `[C24]` and the tutorial shows the idiom: a `None` default and an explicit `if x is None` test in the body `[C23]`. Immutable defaults (numbers, strings, `None`) cannot change. The FAQ also lists tuples as "safe from change", but a tuple holding a mutable object can change `[C6]`, so a tuple default is safe only if all its items are immutable `[C24]`.

**E5** (`e5_function_arguments.py`):

```text
[1]
[1, 0]
[1, 2] [1, 2] ([1, 2],)
[1] [2] (None,)
```

Line 3 shows the bug: both calls returned the same list, and `__defaults__` now contains `[1, 2]`. `[J]` Use `None` for "absent", and a different sentinel only if `None` is a valid argument value.

The same bug exists for dataclass fields. `@dataclass` raises `ValueError` for an unhashable default, and `field(default_factory=list)` creates a new list per instance; the docs call the check a partial solution `[C25]`. **Version-sensitive:** the general "unhashable default" check applies from Python 3.11; earlier versions only rejected `list`, `dict` and `set` defaults `[C25]`.

## Hashing, equality and mutability

- Dict keys and set elements must be hashable; values containing lists, dicts or other mutable types compared by value cannot be keys. Values that compare equal (`1`, `1.0`, `True`) index the same entry `[C26]`.
- Hashing a tuple that contains an unhashable value raises `TypeError` `[C27]`.
- Equal objects must have equal hashes. A class that defines `__eq__` and not `__hash__` has `__hash__` set to `None` and becomes unhashable; a mutable class that defines `__eq__` should not implement `__hash__`, because a key's hash must not change `[C28]`.

## Lifetime and cleanup

Objects are never explicitly destroyed; unreachable objects *may* be garbage-collected, and code must not depend on immediate finalization (close files and connections explicitly with `with`) `[C29]`. `[J]` Aliasing keeps objects reachable, so a long-lived cache or module global holding a reference keeps the object alive (follows from "unreachable objects may be collected").

## Edge cases and failure modes

| Case | Behavior | Evidence |
|---|---|---|
| `nan == nan` | `False`; `nan is nan` `True` | `[C8]`, E1 |
| `[nan] == [nan]`, `nan in [nan]` | `True` on built-in containers, which only "typically" take the identity shortcut | `[C9]`, E1 (observed) |
| `a = 1; b = 1; a is b` | implementation-dependent | `[C11]` |
| `t = ([],); t[0] += [1]` | list mutated first (documented order); the store then raises `TypeError` (observed) | `[C15]`, E3 |
| `[[]] * n` | n references to one list | `[C20]`, E4 |
| `cfg = dict(DEFAULTS)` with nested values | shallow: nested values shared (`dict.copy()` is shallow `[C19]`; `dict()` shown by E7) | E7 |
| `{True: "t"}.get(1)` | same entry: `1 == True` | `[C26]`, E6 |
| `id()` reused | possible after an object dies | `[C3]` |

## Common mistakes and debugging

Mistakes below are drawn from the documented behavior `[Cn]`; the remedies are `[J]` practice.

- **"The list changed behind my back."** Check `a is b` and `id(a), id(b)`. Search for a shared default argument, a module-level container, a `*` repetition, or a shallow copy of nested data.
- **Using `is` for value comparison** (`if x is 5`, `if s is "abc"`) works by accident on some implementations and fails on others `[C11]`.
- **`copy.copy` when you needed `deepcopy`** (nested data still shared), or **`deepcopy` of huge objects on a hot path** (cost; also copies data meant to be shared `[C18]`).
- **Mutating a collection while sharing it as a key or set member** after defining `__hash__` over mutable fields `[C28]`.
- **Returning internal mutable state** from a method or cache: callers can mutate it. Return a copy or an immutable view (judgment).
- Debug tools: `is`, `id()`, `copy.deepcopy`, `f.__defaults__`, and (in a test) asserting `result is not original`.

## Testing methods

`[J]` All of this section is practice, not documented behavior.

- Assert on identity as well as equality where aliasing matters: `assert out is not inp`, `assert out["opts"] is not inp["opts"]`.
- After calling a function with an input fixture, assert the input is unchanged (compare to a `deepcopy` taken before the call).
- Call the function twice and assert the second call is independent of the first (catches mutable defaults).

## Production applications and trade-offs

`[J]` This section is engineering judgment and depends on your application, except where a `[Cn]` tag marks a documented fact. E7 shows the first hazard happening (observed); it does not prove the advice is right for every system.

- **Shared default config across requests.** A module-level `DEFAULTS` dict copied with `dict(DEFAULTS)` is a *shallow* copy: nested dicts and lists are shared `[C19]`. A handler that edits `cfg["options"]` then changes the defaults for every later request. E7 prints `0.9` for the buggy builder and `0.2` for the `deepcopy` version:

  ```text
  after buggy call, module default: 0.9
  after safe call, module default: 0.2
  ```

  Concurrent requests make this worse: the mutation is visible to other in-flight requests (thread-safety is a separate topic).
- **Caches.** If a cache returns the stored object, callers who mutate it corrupt the cache. Options: return copies (cost), return immutable structures (tuple, `frozenset`, `types.MappingProxyType`), or document and test ownership.
- **LLM and AI-engineering code.** Prompt templates, message histories and tool-schema dicts are commonly built from shared base dicts and lists. Appending to a shared `messages` list, or mutating a shared tool schema, leaks one conversation or request into another. Build per-request structures from copies or factories.
- **Defaults in models and schemas.** For dataclasses use `default_factory` `[C25]`. Pydantic and FastAPI have their own copying rules for defaults; this entry does not cover them and they are not verified here.
- **Copy cost vs safety.** Deep-copying at every boundary is safe and expensive; sharing is fast and fragile. Prefer immutable data for configuration, copy at trust boundaries, and avoid copies inside tight loops.
